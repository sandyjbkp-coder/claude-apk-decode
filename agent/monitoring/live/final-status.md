# Final Status — Live Monitoring Instrumentation

## What Was Implemented

Live monitoring instrumentation for the AndroidHarness agent, including:

1. **Log Schema** (`log-schema.json`) — JSONL format with 15 required fields: timestamp, session_id, task_id, agent_id, event_type, command, error, retry_count, memory_used, memory_written, api_call, rate_limit, outcome, latency, cost. Includes redaction rules for secrets and 30-day / 10 MB rotation config.

2. **Metric Schema** (`metric-schema.json`) — 16 metrics across task, API, memory, command, and cost domains: task_success_rate, task_failure_rate, retry_count, retry_budget_usage, api_call_count, rate_limit_hits, 429_count, timeout_count, memory_retrieval_accuracy, memory_write_count, cross_session_recall_rate, fix_reuse_rate, command_failure_rate, tool_usage_rate, latency, cost.

3. **Alert Schema** (`alert-schema.json`) — 8 alerts with severity levels and actions: retry_budget_exhausted (HIGH), api_rate_limit_hit (MEDIUM), repeated_429 (HIGH), memory_retrieval_failure (MEDIUM), memory_write_failure (HIGH), cross_session_recall_failure (HIGH), command_failure_spike (HIGH), task_failure_spike (HIGH).

4. **Instrumentation Plan** (`instrumentation-plan.md`) — 10 instrumentation points: session_start, memory_load, command_executed, error_captured, retry_attempt, fix_applied, memory_write, api_call, rate_limit_event, task_completed.

5. **Implementation Report** (`implementation-report.md`) — Full task-by-task completion report.

6. **Final Status** (`final-status.md`) — This document.

| Instrumentation Point | Event Type | Output |
|----------------------|------------|--------|
| Session Start | session_start | events.jsonl |
| Memory Load | memory_load | events.jsonl |

Output files:
- `agent/logs/events.jsonl` — JSONL logs (rotated, 30-day retention, 10 MB max)

All logs include secret redaction on command, error, stdout, and stderr fields per the redaction rules in log-schema.json. Rotation config: 30-day retention, 10 MB max per file, no secrets in logs, automatic redaction of sensitive data.

## What Alerts Are Active

All 8 alert triggers are defined with severity levels:

| Alert ID | Name | Severity | Trigger Condition |
|----------|------|----------|-------------------|
| A-01 | retry_budget_exhausted | HIGH | retry_budget_usage >= 100% |
| A-02 | api_rate_limit_hit | MEDIUM | rate_limit == true |
| A-03 | repeated_429 | HIGH | 429_count > 3 per session |
| A-04 | memory_retrieval_failure | MEDIUM | memory_retrieval_accuracy < 60% |
| A-05 | memory_write_failure | HIGH | memory write operation returned error |
| A-06 | cross_session_recall_failure | HIGH | cross_session_recall_rate < 60% |
| A-07 | command_failure_spike | HIGH | command_failure_rate > 10 per session |
| A-08 | task_failure_spike | HIGH | task_failure_rate > 10% |

Severity distribution: 6 HIGH, 2 MEDIUM, 0 LOW

Escalation path:
- Agent logs alert to agent/logs/alerts.jsonl
- agent-status shows active alerts
- HIGH severity: user notification required immediately
- MEDIUM: report on next status check
- LOW: log only, no action needed

Evaluation triggers: after every command execution, at session start and end, on retry attempt, on memory read/write, on API call, on rate limit event, on task completion.

## What Dashboards Work

Text-based dashboards are specified for:

- **Task health**: task_success_rate, task_failure_rate, fix_reuse_rate
- **API health**: api_call_count, rate_limit_hits, 429_count, timeout_count, latency
- **Memory health**: memory_retrieval_accuracy, memory_write_count, cross_session_recall_rate
- **Toolchain health**: command_failure_rate, tool_usage_rate, retry_count, retry_budget_usage

Dashboards render on demand from the JSONL log and metric files. Run `agent-status` to see a summary view. Each dashboard is generated by reading metrics from `agent/logs/metrics.jsonl` and formatting as text.

## Whether Improvement Loop Works

The improvement loop is defined end-to-end:

1. **Collect logs** — from all 10 instrumentation points into events.jsonl
2. **Identify failures** — from error_captured and command_executed events
3. **Classify** — by failure type (transient, permanent, configuration, etc.)
4. **Root cause** — from error messages and retry patterns
5. **Update memory** — with learned fixes in memory index
6. **Update retry policy** — based on retry_budget_usage
7. **Update playbook** — with new fix procedures
8. **Re-test** — with updated instrumentation
9. **Deploy** — fixes to live agent
10. **Monitor again** — via dashboards

Tracked in `agent/logs/improvements.jsonl`:
```json
{"timestamp":"ISO","session_id":"<id>","new_patterns":N,"new_fixes":N,"policy_changes":N,"filtered_records":N}
```

The loop runs after every session (automatic) and on demand.
